# CI: what runs, why, and how it changes

One workflow, `.github/workflows/check.yml`, with two jobs. Every pull
request and every push to `main` runs `check`. Only a push to `main`,
after `check` is green, runs `publish`.

## How CI changes

**Agents cannot change this file.** Every agent pushes with one GitHub
token that has the `repo` scope and not `workflow`, and GitHub rejects
any push whose commits touch `.github/workflows/`. It rejects the whole
push, not just that file. A `git push --dry-run` does not catch this,
because the check runs on the payload rather than the access probe, so
read the token's `x-oauth-scopes` header instead.

The scope is withheld on purpose. The same token reaches the arbor
repo, where CI is part of what keeps an agent's change from merging
unreviewed. A token that could edit workflows could weaken that check.

So a CI change is proposed by an agent and applied by the owner:

1. The agent writes the exact YAML, says where it goes, and proves it
   on a clean clone of `main`, all on its Paperclip issue.
2. The owner applies it in a pull request.
3. The owner's standing rule: **a change that only adds new steps or
   jobs is fine; a change that alters an existing step needs the
   owner's explicit decision.** The pull request should say which kind
   it is.
4. The change is recorded here, in the step table below, in the same
   pull request.

## Job `check`

Runs on `ubuntu-latest` for every pull request and every push to
`main`. Steps run in order and the first failure stops the job.

| step | command | what fails it |
| --- | --- | --- |
| checkout | `actions/checkout@v4` | |
| node 22 with npm cache | `actions/setup-node@v4` | |
| install | `npm ci` | a lockfile out of step with `package.json` |
| typecheck and tests | `npm run check` | a type error in any package, or a failing vitest test |
| build | `npm run build` | the web app failing to build |
| bundle size budget | `npm run check:bundle-size` | the built bundle over the budget in `scripts/check-bundle-size.mjs` |
| art check | `npm run art:check` | an art direction failing its colour, contrast or hit-target rules |
| art frames regenerate byte-identical | see below | a frame in `docs/art` whose **pixels** differ from what `tools/art` generates. The step's name is historical; see below for why bytes are the wrong unit |
| no network code in the game bundle | inline shell | `WebSocket(`, `EventSource(` or `sendBeacon(` in the built bundle |

Run the whole job locally, in order:

```bash
npm ci && npm run check && npm run build && npm run check:bundle-size && npm run art:check
```

### The art frames check

`tools/art` is a deterministic generator, and the PNGs in `docs/art/`
are meant to be exactly its output. The step regenerates them and fails
if any frame changed, disappeared, or appeared:

```bash
npm run art:frames
git add --all --intent-to-add -- docs/art
git diff HEAD --exit-code -- docs/art
```

`--intent-to-add` makes a new frame visible to `git diff`, and diffing
against `HEAD` rather than the index keeps a deleted frame visible too.

**What the diff compares is pixels, not bytes, and that is deliberate.**
The bytes are not reproducible. `tools/art/png.ts` compresses through
`node:zlib` `deflateSync(level: 9)`, which is a call into whichever
zlib the running Node was linked against, and two zlib builds emit
different level-9 streams for the same scanlines. Measured on one
x86_64 Linux box with the platform held still and the deflate
parameters pinned to match: Node 24.21.0 (chromium zlib
`1.3.2.1-motley-8002e91`) writes a 12879-byte IDAT for
`fossil-pixel-effects.png` where libz 1.3.1 writes 12878, differing
from byte 6, and both inflate to the same raw buffer. It is per-frame —
`kind-hues.png` agrees between those two — so there is no "arch adds a
byte" rule to learn. The variable is the zlib build, not the OS and not
the architecture.

So `art:frames` **leaves a frame alone when its pixels already match**.
It decodes the committed PNG with `decodePng` and skips the write
unless the pixels differ, which makes the generator idempotent on the
thing it actually determines. The regenerate-and-diff above then cannot
go red because a runner's zlib changed:

- bumping `node-version`, moving to an arm64 runner, or a Node built
  `--shared-zlib` against system libz changes no pixel, so nothing is
  rewritten and the diff stays clean;
- a real change — a frame's pixels, a deleted frame, a frame the
  generator does not produce — still fails it.

That also retires the old rule that frames had to be regenerated on
Linux. **Regenerate art anywhere, including on a Mac.** A changed frame
commits whatever bytes the regenerating machine's zlib produced, and CI
accepts them because the pixels are right.

`npm run art:verify` is the same check without touching the tree: it
decodes every committed frame, compares the pixels, and compares the
set of filenames so a deleted or stray frame fails too. Use it to ask
"is `docs/art` in sync" without a `git status` dance. Its decoder is
covered by `tools/art/test/png.test.ts`, because a decoder that was
wrong towards "equal" would disable the guard in silence.

Two cosmetic edits are owed to `check.yml` the next time the owner
opens it, neither of them load-bearing: the step is named "art frames
regenerate byte-identical" and compares pixels, and its three lines
could collapse to `npm run art:verify` plus nothing else, since
`art:verify` catches every case the diff catches.

### The network-code check

Until `apps/mobile` exists this guards the same bundle the mobile shell
will wrap, so the game stays free of sockets and beacons. Phaser's
loader references XHR, which is allowed here and will be replaced by an
embedded manifest in M3.

## Job `publish`

Runs only on a push to `main`, and only after `check` passes. A pull
request never publishes, since it has no `packages: write` token.

| step | what it does |
| --- | --- |
| checkout, buildx, GHCR login | logs in to `ghcr.io` with the workflow's own `GITHUB_TOKEN` |
| build and push | builds `apps/web/Dockerfile` and pushes `ghcr.io/jukyokim/mazeosaur:<commit sha>` |

The image is **private until the owner ships the game**, by the owner's
decision. The homelab deploy (`JuKyoKim/arbor`, `stacks/beelink/mazeosaur`)
pins one of these sha tags and pulls with a registry credential rather
than anonymously.
